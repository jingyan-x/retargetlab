## 2026-08-12：产品范围重构——v1.0 聚焦 IK/FK 运动学

### 当前共识

1. `v1.0` 建设完整的 Agent-first EEF轨迹本体化与运动学数据处理产品；“完整”强调产品闭环、独立前端、Agent与人工协作、可靠运行、版本谱系、认证和正式交付，不要求同时建成物理仿真平台。
2. `v1.0` 主后端为CuRobo，覆盖IK/FK、连续轨迹、关节与时间约束、自碰撞、静态环境几何碰撞、诊断、Agent有界修复、三维运动学回放、人工微调、鼠标轨迹绘制和标准化导出。
3. `v1.0` 的正式保证止于 `A1 Kinematics Assurance`。静态几何碰撞不等于物理仿真；报告明确声明控制器跟踪、接触、物体动力学和任务成功未验证。
4. SAPIEN、ManiSkill、RoboTwin场景任务、仿真相机及A2/A3验证整体移入后续 `v2.0` 可选仿真扩展，不再阻塞 `v1.0`。
5. `v1.0` 默认安装简化为原生模块化的 `core + curobo`；Linux与Windows/WSL2均走统一安装器。Compose仅作为可选的CI、认证复现或隔离部署方式。
6. RoboTwin可以在 `v1.x` 先提供经过测试的纯数据Schema适配，但必须与RoboTwin仿真或任务验证能力分开声明。
7. 议题2中的“完整产品应具备物理回放”、议题7中的SAPIEN适配包要求、议题8的首版仿真闭环，以及议题9–12中SAPIEN/RoboTwin首发部署和发布要求，均被本次范围重构覆盖，不再属于 `v1.0` 承诺。

## 2026-08-10：议题 1——Agent 介入方式与自治边界

### 当前共识

1. 产品采用 **Agent-first** 工作方式：Agent 承担数据理解、流程规划、工具调用、诊断、候选修复、批量实验、复验和结果整理等主要工作；人负责关键决策、异常处理、最终偏好以及个性化微调。
2. Agent 是流程的规划者和操作员，不是数值求解器。关节轨迹、碰撞结果、动力学结果和质量指标仍由 CuRobo、SAPIEN及确定性数据处理程序生成。
3. 面向用户 Coding Agent 提供配套 Skill 是重要入口。Skill 应调用稳定的项目 CLI 或本地 API，而不是把核心求解逻辑写进 Skill。
4. Web UI 的主要职责转为任务状态展示、回放、候选对比、异常队列、人工审批和个性化微调，而不是让用户手工完成整套处理流程。
5. 自治程度采用多个预设挡位，而不是只有“自动”和“手动”：
   - 流程中设置较多人工确认；
   - Agent 自动处理，人工确认最终回放后导出；
   - 达到既定验收条件后自动导出，失败则转人工；
   - Agent 可在授权范围内自动修复、复验并导出，触及红线或超出预算后转人工。
6. 挡位只改变 Agent 的操作权限和人工检查点，不降低最低验收标准。
7. 界面可以显示简单挡位，但内部应保存完整自治策略，包括允许操作、参数范围、实验预算、验收条件、强制暂停条件、导出权限和抽检策略。
8. 自动处理不得覆盖原始数据；所有修复和导出均应形成可追溯派生版本。“自动导出”也不等于自动下发或执行于真实机器人。

### 仍待讨论

1. 四个挡位的正式名称、默认挡位，以及是否允许项目级默认值和任务级覆盖。
2. 哪些修复属于可自动执行的非语义修改，以及每类修复允许的参数范围和最大轨迹偏移。
3. 坐标系、单位、末端映射、夹爪语义等推断达到何种置信条件后可以自动采用，何时必须暂停。
4. 哪些事件构成不可绕过的人工介入红线，是否允许用户对部分红线提供预授权。
5. 一个机器人配置、数据格式和处理流程满足什么条件后可被标记为“已认证”，并开放更高自治挡位。
6. 自动导出的抽检比例、审计记录粒度、失败实验保留周期和责任边界。
7. Skill 首期是否只支持 Codex，还是从一开始提供可被不同 Coding Agent 复用的通用协议与说明。
8. Agent 会话、实验计划、工具调用、候选比较和人工选择是否全部进入正式任务历史。

### 暂停位置

议题 1 已完成第一轮边界讨论，以上内容暂存为规划输入，后续在自治策略、权限模型和认证机制设计时继续细化。

## 2026-08-10：议题 2——RoboTwin 参考范围与场景任务验证

### 当前共识

1. RoboTwin 主要作为配置化组织和场景任务验证方式的架构参考，不作为当前已经确定的直接依赖。
2. 数据处理主流程不要求每份数据都带有完整场景。只有末端轨迹的数据仍然可以完成 CuRobo 求解、运动学回放、约束检查和导出。
3. 验证能力按三个层级组织：
   - 轨迹有效性验证：IK/FK、连续性、关节限制、自碰撞和时间约束；
   - 场景物理验证：环境碰撞、控制器跟踪、接触、夹取和释放；
   - 任务结果验证：根据场景成功条件判断抓取、放置等操作是否完成。
4. 场景物理验证和任务结果验证均为可选增强阶段，而不是所有数据的必经环节。
5. 没有场景时可以导出，但结果报告必须明确区分“运动学验证通过”和“场景/任务结果未验证”。
6. 数据处理活动与验证场景定义分离：`ProcessingTask` 表示 Agent 处理一批数据的完整活动；可选的 `ValidationScenario` 描述可复用、可版本化的场景、物体、初始状态要求、坐标锚点、接触规则和成功条件；具体一次仿真及其控制器、参数、随机种子和结果由不可变的 `ValidationRun` 记录。
7. 完整产品应具备场景碰撞和物理回放能力，并为任务成功验证提供少量标准模板；当前不把 RoboTwin 的训练和完整 benchmark 范围纳入核心产品。

### 仍待讨论

1. 具体借鉴 RoboTwin 哪些配置结构、运行入口和结果格式，是否需要兼容其部分配置或数据。
2. 仿真任务抽象主要基于原生 SAPIEN，还是更多复用 ManiSkill 的任务接口。
3. 首批标准 `ValidationScenario` 模板覆盖哪些操作任务，以及模板如何与四种机器人组合。
4. 输入数据缺少物体状态、场景标定或夹爪语义时，允许补充到什么程度，哪些内容必须由用户提供或确认。
5. 场景与成功判定器如何版本化、认证和复现。
6. 仿真服务是否从一开始作为独立 worker，以支持本地或远程 GPU 调度。

### 暂停位置

议题 2 已确定总体边界：主流程以轨迹处理和运动学验证为基础，场景物理验证及任务成功验证按数据条件选择性挂载。具体兼容范围和任务模板留待实现设计阶段继续讨论。

## 2026-08-12：议题 3——版本、运行、评估与导出谱系

### 当前共识

1. `ProcessingTask` 是顶层处理活动，一个任务对应固定的输入范围、目标机器人和处理目的；更换其中任一核心目标时新建或复制任务。
2. 核心对象保持精简：`SourceAsset`、`CanonicalTrajectoryVersion`、`RobotProfileVersion`、`SolveRecipe`、`ReplayRun`、`ChangeProposal`、`ExperimentBatch`、可选的 `ValidationScenarioVersion` 与 `ValidationRun`、`EvaluationPolicyVersion`、`EvaluationRun`、`ReviewDecision`、`AutonomyPolicySnapshot` 和 `ExportBundle`。
3. 配置与执行分离：配置修改产生新版本，每次执行产生不可变 Run；原始数据和历史产物不得覆盖。
4. 验证场景与验证运行分离：场景定义可复用和版本化，控制器、仿真参数、随机种子、运行事件和结果属于具体 `ValidationRun`。
5. Agent 修复先形成 `ChangeProposal` 和候选实验；即使处于高自治挡位，也必须保留修改内容、原因、实验预算和指标变化。
6. 运行、评估、决策和导出职责分离：Run 保存客观事实，`EvaluationRun` 使用指定版本的规则解释事实，`ReviewDecision` 负责授权，`ExportBundle` 冻结最终结果。
7. 上游变化不删除或否定旧结果。旧结果仍对原依赖有效，但不再适用于当前任务组合；系统分别推导 `NEEDS_RECOMPUTE`、`NEEDS_REEVALUATION`、`NEEDS_REVIEW` 和 `READY_TO_EXPORT`。
8. 依赖影响按字段分类：展示元数据不触发重算；验收规则变化触发重评；场景或仿真配置变化只重跑 `ValidationRun`；轨迹、机器人运动学配置或求解配方变化重跑 `ReplayRun` 及其下游。
9. 每个 Run 根据输入内容、依赖版本、软件环境、确定性设置和随机种子生成指纹；指纹完全一致时允许安全复用结果。
10. 自动放行由版本化规则和自治策略裁决，不由 Agent 自行宣称通过。人工覆盖警告必须记录原因，硬性失败不可被普通覆盖。
11. 创建 `ExportBundle` 必须通过原子门禁，并使用任务修订号防止验收与导出之间发生并发配置变化。旧导出包永久冻结；返工产生新的 Run、决策和导出包。
12. 原始数据、配置版本、决策记录、依赖清单和导出清单长期保留；未引用的大型视频、仿真状态和缓存可按策略清理，但保留元数据、指纹和 `payload_evicted` 状态。

### 实现期再确定

1. 对象、字段和状态枚举的最终命名，以及存储 Schema 的具体形式。
2. 各配置字段属于 `metadata_only`、`evaluation_affecting`、`simulation_affecting` 或 `kinematics_affecting` 的完整映射表。
3. Run 指纹采用的规范化序列化方法、软件环境粒度和跨版本缓存兼容策略。
4. 用户覆盖的具体权限模型，以及哪些验收项属于绝对不可覆盖的硬失败。
5. 大型运行载荷的默认保留期限、容量上限和清理策略。
6. `ProcessingTask` 的最终状态枚举与界面文案；运行状态尽量由产物推导，`PAUSED`、`CANCELLED`、`ARCHIVED` 等用户意图单独保存。

### 暂停位置

议题 3 的核心设计已经闭环，不再继续增加版本对象。后续工作属于 Schema、状态枚举、字段影响表和存储策略的实现细化，不影响当前总体架构。

## 2026-08-12：议题 4——验收、评分、认证与发布评估

### 当前共识

#### 1. 三类验收对象

1. 单次处理结果验收：判断当前候选对指定输入、机器人和任务目标是否可采用及导出。
2. 配置组合认证：判断一个版本化自动工作流在明确适用范围内是否足够可信，并决定可开放的自治上限。
3. 产品发布验收：判断整个软件版本、四种机器人覆盖、Agent 闭环、可复现性和端到端产品能力是否达到发布要求。
4. 真实机器人安全验收不属于本工具的仿真结论。系统只能声明运动学验证、场景物理验证和任务成功验证的实际执行情况，不能把 CuRobo 或 SAPIEN 通过表述为真实机器人安全可执行。

#### 2. 单次结果采用硬门槛与质量评分

1. `EvaluationRun` 分别输出 `GateStatus`、`AssuranceLevel`、`QualityDimensions`、`RankingScore` 和 `EvaluationCoverage`。
2. 硬门槛决定候选能否采用，质量评分只在合格候选之间比较；任何软指标高分都不能抵消硬失败。
3. `GateStatus` 至少区分 `PASS`、`PASS_WITH_WARNINGS`、`REVIEW_REQUIRED` 和 `FAIL`。高自治挡位默认只自动导出 `PASS`；警告是否允许自动放行由自治策略明确授权。
4. 全局硬门槛包括数据语义明确、必要区间可解、机器人硬约束未违反、关键帧和任务事件未被破坏、修复偏移在授权范围内、要求的验证层级已经执行以及完整可追溯。
5. 质量评分保留至少五个分项：`Fidelity`、`MotionQuality`、`ConstraintMargin`、`TrackingRobustness` 和 `RepairPreservation`。
6. 可提供 `RankingScore` 辅助排序，但不以单一总分代替分项指标，也不以总分决定通过与否。
7. 总分由版本化 `ScoringProfile` 决定，可支持忠实度优先、平滑运动、鲁棒执行、最小修复和任务特定等策略。
8. 候选只有在机器人、处理目标、评估规则、评分规则和验证深度相同时才可直接比较。缺失验证标记为 `NOT_EVALUATED`，不能按零分处理或通过改权重隐藏。
9. Agent 选择候选时先过滤硬失败和验证深度不足，再检查明显短板和任务优先级，最后才使用总分打破接近候选；差异属于用户偏好时按自治挡位自动选择或升级人工。

#### 3. 验证深度独立表达

1. `A1`：运动学与轨迹约束验证。
2. `A2`：场景物理和控制器跟踪验证。
3. `A3`：任务结果验证。
4. 验证深度描述证据覆盖范围，不与质量分混合；仅完成 A1 的高分候选不能被描述成已完成 A2 或 A3。

#### 4. 评估规则采用三层组合

1. 最终 `EvaluationPolicySnapshot` 由全局基础规则、`RobotProfile` 认证规则和任务/场景规则组合而成。
2. 全局层统一规则类型和不可绕过原则，例如数据合法、语义明确、硬约束遵守和可追溯；具体数值不必跨机器人统一。
3. `RobotProfile` 提供关节、速度、加速度、jerk、力矩、碰撞、奇异性和控制器等经认证的限制与基线。
4. 任务/场景规则提供 EEF 允许误差、关键帧、修复范围、接触规则、成功条件和扰动测试要求。
5. 三层约束按交集生效：任务可以收紧要求，但不能放宽机器人的物理硬限制。任务要求超出机器人能力时应在运行前报告配置不可满足。
6. 跨机器人比较应同时保留原始指标和按各自限制归一化的指标，只在相同任务及验证深度下比较归一化质量维度。

#### 5. 认证版本化自动工作流

1. 不笼统认证机器人名称，而是认证一个有明确边界的 `CertifiedWorkflow`，至少绑定 `RobotProfileVersion`、`DataAdapterVersion`、`SolveRecipeTemplate`、CuRobo及运行环境版本、可选控制器与验证场景类别、支持范围、Agent 可修改参数范围和测试套件版本。
2. 认证等级分为：`T0` 未验证、`T1` 回放验证、`T2` 自动直出、`T3` 自动修复。
3. 认证等级只是自治权限上限。实际权限等于用户所选挡位、当前认证能力和任务/场景限制的交集。
4. 认证覆盖模型一致性、正向样例、负向样例、边界与复现、自动修复专项，以及双臂、移动或人形等形态专项测试。
5. 认证针对模板和参数有效范围，而不是穷举每个参数组合。超出认证范围必须降级到人工确认或重新认证。
6. 修改展示元数据不影响认证；修改关节限制、坐标变换或碰撞模型需要重测；升级 CuRobo、SAPIEN 或控制器至少运行兼容性测试；修改硬门槛或自动修复范围需要重新认证相关 T2/T3 能力。

#### 6. 产品发布验收

1. 发布采用阻断项、质量指标和能力覆盖声明，不能用总分掩盖严重失败。
2. 发布阻断项包括历史产物不可覆盖、结果可复现、负向样例不被错误放行、Agent 不得越权、全流程可追溯、并发修改不会导致错误导出、worker 失败不会产生伪成功、导出清单一致以及数据迁移不静默改变历史结果。
3. 官方负向测试集中的硬失败错误放行数必须为零；该结论只适用于实际测试范围，不宣称对未知数据绝对安全。
4. 四种机器人分别覆盖可达、边界、不可达、奇异、越界、自碰撞和环境碰撞、不连续、时间非法以及 Agent 正确修复和正确放弃案例；一种机器人的大量通过不能抵消另一种机器人的失败。
5. Agent-first 发布测试覆盖理解输入、制定计划、工具调用、失败诊断、受限实验、候选选择或升级人工、复评、审批和导出完整闭环。
6. 端到端验收覆盖 Coding Agent Skill、CLI/API、Web UI、四个自治挡位、中断重试取消、缓存和存储清理，以及人工接管能力。
7. 每次发布生成 `ReleaseEvidenceManifest`，列明软件环境、测试套件、各机器人认证等级、支持范围、验证层级、Agent 自治上限和已知限制。
8. 正式全量版本要求四种机器人至少达到 T1；承诺达标自动导出的组合必须达到 T2；只有通过自动修复专项测试的组合才能标记 T3。

#### 7. 测试集与阈值制定

1. 测试集由基础契约测试、参数化机器人测试、Agent 修复挑战集和真实问题回归集组成。
2. 每个 `CaseManifest` 明确输入哈希、适用机器人、验证深度、预期门禁结果、必须检测的问题、允许修复、禁止修改的语义、实验预算和判定 Oracle。
3. IK 存在多解时不要求输出等于某条固定关节轨迹，而验证 EEF 误差、连续性、约束、碰撞、任务结果和修复范围等性质。
4. 测试资产分为公开一致性测试、参数化随机压力测试、冻结认证集和真实问题回归集；随机测试保存种子以便复现。
5. 阈值必须注明来源：机器人硬限制来自认证后的 `RobotProfile`；数值容差来自跨后端一致性和重复噪声标定；任务忠实度来自任务或用户目标；质量警告线来自合格样例分布；仿真成功率来自多种子试验及置信区间；性能阈值按硬件档位制定。
6. 阈值通过正负样例采集、误差分布分析、优先避免错误放行、随机和冻结集验证、人工审核后冻结为 `EvaluationPolicyVersion`，不得反复使用最终认证集调参。
7. 核心发布指标包括 `False Pass`、`False Reject`、`Escalation Accuracy`、`Repair Success` 和 `Reproducibility`。

### 实现与标定阶段再确定

### 暂停位置

## 2026-08-12：议题 5——Agent 执行闭环与人工接管

### 当前共识

1. 用户自己的 Coding Agent 加配套 Skill 是主要智能入口，负责理解目标、制定计划、读取诊断、提出修复、组织实验和无人值守编排；项目核心不重复建设内置 Agent Runtime。
2. 独立前端应用是与 Coding Agent 并列的完整入口，采用 React、TypeScript 和 R3F，通过统一 API 进行人工操作、监督、审批、回放、候选比较、个性化微调与随时接管；完整版不以 Viser 或后端附带页面作为主界面。
3. Coding Agent、独立前端和其他客户端共用统一 CLI/本地 API、任务状态、权限、版本谱系和审计记录。
4. `Task Orchestrator` 是非 AI 的权威控制层，负责持久化任务和计划、校验权限与认证范围、管理预算、调度和恢复 worker、控制并发与导出门禁，以及保存结构化调用记录。
5. CuRobo、SAPIEN、Evaluator 和 Exporter 等 worker 只执行确定性计算。Agent 只能提交结构化配置与受控操作，不能直接生成或伪造数值结果。
6. 项目支持原子工具调用和声明式 `ExecutionPlan` 两种方式；无人值守和批量处理主要使用后者。
7. `ExecutionPlan` 至少绑定任务修订号、目标、自治策略快照、总预算和步骤依赖；每一步声明白名单操作、输入与配置引用、预期产物、审批要求、失败策略和幂等键。
8. `ExecutionPlan` 不保存 Agent 的思维过程，不接受任意 Shell、Python 或自定义求解代码。允许操作由项目工具契约显式定义。
9. Orchestrator 激活计划前检查 Schema、依赖引用、任务修订、自治权限、认证范围、参数边界、资源预算、强制人工检查点和不可覆盖规则；系统可以追加确认点，Agent 不能绕过确认点。
10. 自动修复搜索使用有界 `ExperimentBatch`，明确参数空间、最大候选数、运行时间、停止条件、过滤条件和排序规则，不允许无限自主循环。
11. 已激活计划不可原地修改。修改产生新的 `PlanRevision`，保留已完成步骤和产物，并将因依赖变化而不再执行的步骤标记为 `SUPERSEDED`。
12. Worker 崩溃时幂等步骤可按策略重试；Agent 断开时已提交的确定性步骤继续执行；人工修改导致依赖变化时相关待执行步骤暂停；导出采用临时构建与原子发布，不留下半成品。
13. 任何 Coding Agent 均可通过统一 `TaskSnapshot` 接力，读取当前目标、任务版本、活动计划、完成步骤、候选与评估、失败诊断、待决事项、剩余预算和下一步允许操作，无需依赖原聊天记录。
14. 人工直接操作同样遵守版本、Run、评估和审批体系；人工修改产生新版本，人工运行产生不可变 Run，Agent 重新接手时从人工结果继续。

### 实现期再确定

1. `ExecutionPlan`、步骤状态、错误码和 `TaskSnapshot` 的最终 Schema 与命名。
2. CLI 命令、REST/WebSocket 接口和 Skill 工具说明的具体形式。
3. 各操作的默认超时、重试、取消、幂等和 worker 租约规则。
4. 多客户端同时操作时的锁、乐观并发和冲突提示细节。
5. Coding Agent 的认证、访问令牌、最小权限和本地 API 安全策略。
6. Skill 首批支持的 Coding Agent、安装方式、版本兼容和升级流程。
7. 未来是否以非核心插件形式提供项目托管的 Agent Runtime；当前全量首版不依赖该能力。

### 暂停位置

议题 5 的执行闭环已经闭合：用户 Coding Agent 负责智能决策和无人值守编排，独立前端负责完整人工操作与接管，Orchestrator 负责可信执行和恢复，worker 负责确定性计算。剩余内容属于接口与运行时实现细化。

## 2026-08-12：议题 6——输入范围与语义契约

### 当前共识

1. 输入支持分为三层：项目原生标准 Schema、通过 `MappingSpec` 接入的 CSV/JSON/HDF5/Zarr 等通用容器，以及通过版本化 `DataAdapter` 接入的 LeRobot、RoboTwin 等固定数据集格式。容器格式本身不代表已经兼容其内部 Schema。
2. 所有输入在求解前统一生成不可变的 `CanonicalTrajectoryVersion`；项目主线仍是 EEF 轨迹，图像、深度、力、物体状态等作为可选同步通道。
3. 最低语义契约按处理模式决定：位置路径需要顺序、位置、单位、参考坐标系、绝对/相对语义和工具点；位姿、原时间、夹爪及场景任务模式分别增加对应的必要语义。
4. 每项语义记录证据来源：`EXPLICIT`、`ADAPTER_CERTIFIED`、`DERIVED`、`INFERRED_CANDIDATE` 或 `USER_CONFIRMED`。前三类可直接进入自动流程；未经确认的 Agent 推断只能用于预览和候选实验。
5. Agent 可以自动扫描字段、匹配已知 Schema、执行明确单位转换、规范化四元数、由采样率生成时间戳、检测异常，以及提出带证据和置信度的语义候选。
6. 没有明确证据时，单位尺度、参考坐标系、绝对或相对轨迹、四元数分量顺序、工具点定义和夹爪语义不得被静默采用；即使处于高自治挡位，也必须由认证适配器、项目模板或用户确认解决。
7. 缺少姿态时进入位置约束模式，不自动编造姿态；缺少时间时作为几何路径重新定时，不声称保留原速度；缺少夹爪或场景数据时分别不声明抓取任务或 A2/A3 验证通过。
8. 严重缺失、乱序或跳变可以由 Agent 提出受限修复候选，但必须保留原始区间、修复范围、方法和指标变化。
9. 每次导入保存 `SourceAsset`、`DataAdapterVersion`、`MappingSpecVersion`、`SemanticManifest`、`CanonicalTrajectoryVersion` 和 `InputQualityReport` 的完整谱系；字段映射或语义确认变化生成新版本，不覆盖旧版本。
10. 标准导入流程为只读检查、适配器匹配或字段映射、语义证据提取、确定项自动处理、歧义候选预览、必要人工确认、规范轨迹生成和契约预检。

### 实现期再确定

1. `CanonicalTrajectory`、`SemanticManifest`、`MappingSpec` 和 `InputQualityReport` 的最终字段、Schema 版本和序列化格式。
2. 首批 CSV/JSON/HDF5/Zarr 映射能力和 LeRobot、RoboTwin 等数据适配器的具体版本范围。
3. 语义候选置信度的计算、展示和人工确认交互。
4. 姿态缺失、时间缺失、异常值与缺失段的默认候选修复方法及参数范围。
5. 大规模数组、同步图像和多模态通道的加载、索引、缓存和流式处理策略。
6. 各处理模式的精确必填项、预检错误码和降级验证声明。

### 暂停位置

议题 6 的输入边界已经闭环：系统尽可能自动完成字段识别和规范化，但未经可靠证据确认的数据语义不得静默进入正式自动流程。剩余工作属于 Schema、适配器和交互实现。

## 2026-08-12：议题 7——机器人适配契约与多运动组

### 当前共识

1. 所有机器人使用统一 `RobotProfile` 契约，不为单臂、双臂和移动/人形形态建立彼此割裂的接口。机器人由一个或多个可控制 `KinematicGroup` 组成，而不是默认只有一条机械臂。
2. `RobotProfile` 至少组织共享机器人资产、运动组、末端执行器、执行器、底座模型、碰撞模型、后端绑定和能力清单。
3. URDF 是 CuRobo 与 SAPIEN 共享的主要机器人结构资产，但两个后端保留各自所需的派生配置，通过显式的 joint、link、root、TCP 和坐标映射保持一致。
4. `KinematicGroup` 显式声明关节链、根节点、末端、关节顺序、求解模式及受控自由度；`EndEffector` 区分法兰、TCP、夹爪中心和工具偏移。
5. `BaseModel` 明确固定底座、平面移动或其他被支持的根自由度；未支持自由度必须锁定或拒绝，不能隐式近似为已经支持。
6. `CapabilityManifest` 对位置/位姿 IK、夹爪、双臂同步、场景验证、移动底座、全身平衡等能力分别标记 `SUPPORTED`、`CONDITIONALLY_SUPPORTED` 或 `NOT_SUPPORTED`。模型可加载不等于能力已适配或认证。
7. 单个 `ProcessingTask` 可以同时绑定多个源轨迹通道和多个运动组。每个 `EmbodimentBinding` 显式记录源通道、目标运动组、目标末端、坐标变换、约束模式和同步组。
8. 多运动组同步支持 `LOCKSTEP`、`TIME_ALIGNED`、`EVENT_ALIGNED` 和 `INDEPENDENT`，并根据声明检查臂间碰撞、相对末端约束、共享物体约束、任务事件顺序和时间一致性。
9. ALOHA 以左右臂和左右夹爪等多个运动组表达；第四种移动/人形代表只承诺项目实际实现并认证的运动范围，不把本工具扩展为通用步态或全身控制框架。
10. 每种机器人交付版本化适配包，包含 Robot Profile、URDF及资源、CuRobo配置、SAPIEN配置、控制器、标定和认证资产。
11. 机器人适配包必须通过资产完整性、关节/link映射、CuRobo与SAPIEN FK一致性、限位与碰撞配置、EEF/TCP标定和形态专项认证测试。

### 暂停位置

## 2026-08-12：议题 8——CuRobo、SAPIEN 与 ManiSkill 仿真边界

### 当前共识

1. CuRobo 负责将规范 EEF 轨迹编译为机器人关节轨迹，执行运动学约束、关节限制、连续性和规划阶段碰撞检查，生成 `ReplayRun`；它不直接宣称物理控制或任务成功。
2. SAPIEN 是统一物理验证底座，负责加载机器人与场景、通过认证控制器跟踪轨迹、检查动态碰撞和接触、记录跟踪误差、力矩与物体状态，并生成 `ValidationRun`。
3. ManiSkill 是 SAPIEN 之上的可选任务层，用于复用标准场景、初始化、随机化、批量评估和成功判定；空场景跟踪、环境碰撞和自定义场景验证不强制依赖 ManiSkill。
4. CuRobo 与 SAPIEN 通过版本化 `ReplayArtifact` 交接，至少包含 joint names、时间戳、q/qd/可选 qdd、底座轨迹、夹爪通道、任务事件、机器人版本、坐标语义和来源谱系。映射必须按 joint name 完成，不能依赖数组顺序偶然一致。
5. 控制验证区分运动学/几何回放、位置或 PD 控制，以及经 Robot Profile 认证的其他控制器。A1 不要求 SAPIEN；A2 至少运行认证控制器；A3 在此基础上增加任务成功条件。
6. CuRobo 与 SAPIEN 引用同一版本化 `SceneSnapshot`，并分别保存派生碰撞几何和哈希。场景快照包含机器人、障碍物几何、物体位姿、坐标变换、接触策略和安全裕量。
7. `CollisionPolicy` 显式区分 `PROHIBITED`、`ALLOWED`、`REQUIRED` 和 `IGNORED` 接触。任务所需接触必须由场景规则预先定义，不能由 Agent 在碰撞发生后临时解释。
8. 任一后端发现禁止碰撞，都不能被另一后端的“未发现”直接覆盖。CuRobo无碰撞而SAPIEN发生禁止接触时A2硬失败；CuRobo报警而SAPIEN未接触时进入 `MODEL_DIVERGENCE`，按一致性容差诊断、重算或升级人工。
9. 每个机器人适配包必须包含 CuRobo 与 SAPIEN 的 FK、关节映射、坐标、碰撞对和距离报警一致性测试；超出认证容差时暂停对应自动直出资格。
10. 仿真运行分为：`S0 Geometry Replay` 用于快速候选筛选；`S1 Deterministic Control` 用固定初态、控制器、物理参数和种子完成标准A2；`S2 Robustness Campaign` 用多种子和有边界扰动完成高可信A2/A3。
11. S2 的扰动范围由版本化 `RobustnessProfile` 声明，可涵盖初始关节、物体位姿、物理参数、控制延迟、噪声和事件偏差。输出成功率、置信区间、最差指标、禁止碰撞率、失败分布和最差运行引用。
12. 计算按 S0 大量筛选、S1 少量验证、S2 最终候选逐级升级；硬失败时不继续浪费后续预算，S2支持基于通过概率和置信区间的可复现早停。
13. 每个 `ValidationRun` 使用独立进程上下文和运行目录；共享资产只能只读。Worker崩溃不得污染其他Run或任务历史。
14. Orchestrator 通过带期限的 `RunLease` 分配运行，使用心跳、attempt 和 input fingerprint 防止重复提交；结果采用临时产物、完整性与哈希校验、原子提交的两阶段流程。
15. 并发调度按 GPU显存、CPU、内存、临时磁盘、场景资产和渲染需求声明资源。CuRobo优先使用批处理；S2拆分为独立种子Run并由 `RobustnessCampaign` 聚合。
16. 每次仿真冻结输入哈希、机器人与场景版本、SAPIEN/ManiSkill、控制器、物理参数、频率、种子、扰动值、环境指纹、GPU驱动和确定性设置，并声明 `BITWISE_REPRODUCIBLE`、`TOLERANCE_REPRODUCIBLE` 或 `STATISTICALLY_REPRODUCIBLE`。
17. 失败区分 `INFRA_FAILURE`、`CONFIG_FAILURE`、`VALIDATION_FAILURE` 和 `CANCELLED`。只有基础设施失败按相同指纹重试；参数变化必须创建新Run，验证失败是有效结果而非自动重试理由。
18. `ValidationRun` 至少保留门禁证据、时间对齐事件、失败区间、目标/实际关节轨迹、场景状态摘要、完整Manifest与产物哈希；大型视频和状态载荷可清理，但决定结论的结构化证据不得删除。

### 实现期再确定

1. `ReplayArtifact`、`SceneSnapshot`、`CollisionPolicy`、`RobustnessProfile` 和 `ValidationRun` 的最终 Schema。
2. 首批认证控制器、SAPIEN 时间步长、控制频率及每种机器人的控制参数。
3. ManiSkill 首批复用的任务模板，以及哪些场景使用原生 SAPIEN 实现。
4. CuRobo 与 SAPIEN 碰撞模型一致性容差、模型差异诊断工具和人工处理界面。
5. S2 扰动分布、种子数量、置信区间和早停规则。
6. Worker资源估算、隔离方式、录制策略和复现等级的具体实现。

### 暂停位置

议题 8 的仿真实现边界已经闭环：CuRobo编译和预检轨迹，SAPIEN执行分级物理验证，ManiSkill按需提供任务抽象；两端分歧进入显式一致性诊断，仿真Run以隔离、租约、原子提交和声明式复现方式运行。

## 待讨论提案：议题 9——本地、自托管与 GPU Worker 部署

> 本节是后续讨论提案，不是已经确认的架构结论。

### 推荐方案

1. 产品保持本地优先、自托管，不做由项目方承担算力的 SaaS；联网仅用于用户自行选择的 Coding Agent、依赖获取、远程服务器访问或未来插件。
2. 采用统一单节点拓扑作为首个正式支持目标：

```text
Browser / Coding Agent
        ↓ localhost 或受控远程连接
React Frontend + FastAPI / Task Orchestrator
        ↓ 持久任务队列
CuRobo Worker + SAPIEN Worker
        ↓
SQLite元数据 + 文件制品存储
```

3. FastAPI、Orchestrator和项目索引可先在一个后端服务中实现，不为了“全量版本”过早拆成微服务；CuRobo和SAPIEN因GPU生命周期、依赖与故障隔离而使用独立长生命周期进程或容器。
4. 元数据、任务状态、租约、索引和审计记录使用 SQLite；大数组、轨迹、视频和仿真状态写入版本化文件制品，不把逐帧数值塞进关系数据库。
5. 使用持久化数据库队列和Run租约支持重启恢复，不在首个正式实现中强制引入 Redis/Celery；接口保留未来多节点调度扩展能力。
6. REST用于命令、查询和对象管理；WebSocket用于任务事件、日志、实时进度和交互回放状态。大数组和视频通过制品URL、范围读取或流式文件接口传输，不塞进WebSocket消息。
7. 官方发布使用版本锁定的 NVIDIA Container/Compose 配置；开发者可以使用 `uv`、`pnpm` 和本地进程运行。CuRobo与SAPIEN可以使用不同镜像，避免CUDA、PyTorch和仿真依赖互相污染。
8. Windows用户通过 WSL2 + NVIDIA GPU 运行后端和worker，独立前端通过本机浏览器访问；Ubuntu + NVIDIA为原生Linux路径。高频运行数据优先保存在Linux文件系统或容器卷中，导出时再写入用户选择的主机目录。
9. 远程实验室GPU服务器运行同一套完整自托管栈，用户通过HTTPS、VPN或SSH隧道访问；不是把本地Orchestrator与任意公网worker拼成分布式云平台。
10. 默认只监听本机地址并生成本地访问凭据；开启LAN/远程访问时必须启用身份验证、项目路径沙箱、允许来源配置和TLS或受保护隧道。
11. 调度器按GPU显存、CPU、内存、磁盘、渲染需求和worker能力标签分配任务，并在前端和TaskSnapshot中展示排队原因、资源占用与预计成本。
12. 版本升级通过数据库迁移、Schema兼容检查、worker能力握手和旧Run只读验证完成；worker版本不匹配时拒绝运行，不能静默使用不同环境。

### 需要用户确认

1. **[已确认目标、兼容风险待解 9-A] 官方首发环境**：产品目标是完整支持 Ubuntu/Linux + NVIDIA，以及 Windows 11 + WSL2 + NVIDIA。经核对，RoboTwin 2.0官方当前声明WSL仅支持CPU仿真，不支持GPU仿真与渲染，因此“WSL完整A2/A3与RoboTwin能力”目前不能直接依赖上游实现；需要通过本项目实测、Windows/WSL混合worker或远程Linux仿真方案解决后才能形成正式支持声明。macOS及非NVIDIA GPU不列为完整CuRobo能力环境。
2. **[已确认 9-B] 分布式范围**：不建设跨多台机器的分布式 GPU worker、动态注册、共享制品存储或集群调度。正式支持本机单节点，以及将整套栈部署到一台远程 Linux GPU 服务器后访问；worker协议只服务于同一部署实例内的进程/容器隔离，不把未来分布式扩展作为当前产品负担。
3. **[讨论中 9-C] 官方安装形式**：建议Container/Compose作为本产品的用户发布主路径，原生 `uv + pnpm` 作为开发路径，并由Tauri桌面壳隐藏启动细节。RoboTwin 2.0官方当前采用Python 3.10 Conda环境、递归克隆XPolicyLab子模块、`scripts/_install.sh`安装基础环境与CuRobo、`scripts/_download_assets.sh`下载资产；Docker文档只给出Vulkan/NVIDIA graphics能力等附加要求，没有提供可直接复用的官方Compose交付。因此本项目若采用Compose，需要自行构建并锁定独立RoboTwin/SAPIEN worker镜像及资产管理流程。

## 待讨论提案：议题 10——Agent-first 独立前端

> 本节是后续讨论提案，不是已经确认的界面定稿。

### 推荐方案

1. 独立前端采用 React、TypeScript和R3F，是完整人工操作、监督和接管入口；它不是Viser页面，也不是围绕聊天框构建的Agent壳。
2. 默认体验以任务和异常为中心：Agent负责推进，用户首先看到任务状态、当前候选、阻断原因、待确认项和下一步，而不是逐项填写长表单。
3. 前端至少包含以下工作区：
   - 项目与批任务看板；
   - 导入数据、字段映射和语义证据；
   - Agent计划、执行时间线、预算和工具调用；
   - 3D机器人/场景回放、同步时间轴和关节/EEF曲线；
   - 诊断问题区间和失败证据；
   - 候选并排比较、差异解释和选择；
   - 人工微调、关键帧和任务事件；
   - 仿真、评估、认证与验证深度；
   - 版本谱系、审批、导出和审计记录。
4. 界面提供“概览/审核”和“专家编辑”两种信息密度。自治挡位控制Agent权限，界面模式只控制展示复杂度，两者不得混为一谈。
5. 3D回放与时间轴共享统一播放时钟，能够叠加源EEF、目标EEF、实际FK、多个候选、碰撞点、接触事件、关键帧和场景物体状态。
6. 人工微调优先编辑任务空间约束、EEF关键帧、允许偏差、坐标变换、事件和处理参数；所有编辑形成结构化 `ChangeProposal` 或新版本，并自动触发依赖重算。
7. 关节空间直接修改只放在专家模式，必须清晰显示其对EEF忠实度、连续性和约束的影响，修改后强制重新评估，不能作为绕过求解器和门禁的捷径。
8. 候选比较同时展示同步回放、分项指标、验证深度、修改范围、失败区间和Agent选择理由；不使用单一总分替代证据。
9. 人工确认采用可处理的决策卡片，明确“为什么需要人”“有哪些候选”“若不处理会怎样”和“该决定会生成什么版本”，避免只弹出确认框。
10. 前端状态以服务端任务和版本为权威来源；TanStack Query一类服务端状态层负责同步，局部播放、镜头和选择状态可以保存在前端，不允许在浏览器内维护另一套任务真相。
11. 断线重连后通过TaskSnapshot和事件游标恢复；长任务关闭页面仍可继续运行。多客户端发生冲突时显示任务修订差异并要求刷新或基于新版本重新提交。
12. 批处理界面支持按错误类型、机器人、认证范围、验证深度和待确认原因筛选，允许用户一次批准同类非语义操作，但硬红线仍逐任务阻断。

### 需要用户确认

1. **[已确认 10-A] 首发载体**：完整 React、TypeScript和R3F前端同时提供 Tauri 桌面壳，作为 Windows/Linux 本地正式入口；保留同一前端的浏览器访问，用于远程 Linux GPU 服务器、调试和故障排查。Windows桌面壳负责检查并启动 WSL2 中的后端、等待健康检查并处理主机/WSL路径映射。
2. **[需确认 10-B] 人工微调深度**：建议首发完整支持EEF关键帧、约束、事件、坐标和参数微调；关节空间编辑提供专家能力，但不建设类似专业动画软件的完整曲线编辑器。
3. **[已确认 10-C] 批量审批**：允许对相同适配器、相同认证工作流、相同非语义警告和相同处理策略批量确认；坐标/单位/TCP等语义不明、任务意图差异和硬约束相关事项禁止批量放行。

## 待讨论提案：议题 11——导出包与生态适配

> 本节是后续讨论提案，不是已经承诺的首发格式列表。

### 推荐方案

1. 所有外部格式之前先生成唯一权威的 `CanonicalExportBundle`。生态Exporter只从该冻结包转换，不能绕过版本、评估和导出门禁直接读取临时Run。
2. 导出包至少包含：

```text
manifest.json
trajectory/         目标关节、EEF、时间、底座与夹爪通道
events/             关键帧、夹爪、任务阶段、碰撞与质量事件
profiles/           Robot/Solve/Scene/Evaluation/Autonomy快照或哈希
metrics/            分项指标、Gate、Assurance和覆盖率
provenance/         输入、适配、计划、Run、决策与软件环境
validation/         可选仿真和鲁棒性证据
media/              可选视频、缩略图和调试载荷
checksums.json
```

3. 数值通道必须保存joint names、单位、坐标系、四元数顺序、时间语义、root/base处理、缺失值规则和采样方式，不能只导出无Schema的数组。
4. 每个导出包声明实际验证深度A1/A2/A3、机器人工作流认证等级T0-T3、警告与未执行检查；不能用“validated”笼统掩盖证据范围。
5. 导出采用临时目录、完整性检查、哈希和原子发布；同名目标默认创建新版本，不覆盖旧包。批量导出支持断点恢复和逐条Manifest。
6. `ExportAdapter` 必须声明目标格式版本、字段映射、单位转换、丢失字段和不支持能力。任何有损转换都生成机器可读警告并进入导出报告。
7. 外部格式适配至少分为：
   - 通用分析与交换：CSV/JSON加结构化Manifest，HDF5/Zarr/Parquet按数据规模选择；
   - 训练生态：LeRobot数据适配；
   - 仿真/benchmark生态：RoboTwin任务或数据适配；
   - 机器人日志生态：按真实需求增加MCAP等格式。
8. 适配器需要契约测试、目标格式校验和可行时的往返测试。目标库版本变化时旧适配器继续按原版本工作，新版本另行认证。
9. 原始输入可选择复制、硬链接或只保存内容寻址引用；导出Manifest必须说明模式，避免看似自包含但实际缺文件。
10. 导出结果只用于数据处理、训练或仿真生态，不包含自动向真实机器人下发命令的接口。真机执行属于单独产品边界和安全审批。

### 需要用户确认

1. **[已确认 11-A] 生态范围**：RoboTwin作为正式适配目标，针对明确的版本、任务和Schema实现并测试，不做名义兼容；Canonical与通用格式的具体首发清单仍在实现规划中冻结。
2. **[需确认 11-B] 自包含策略**：建议正式导出默认自包含关键轨迹、配置和证据；大体积原始视频允许内容寻址引用，并提供“完全自包含”可选项。
3. **[已确认 11-C] 训练数据范围**：完整多模态训练episode重组暂不作为首发硬要求，但在 Schema、同步通道、制品引用和适配器接口中预留后续扩展位。首发优先保证机器人action/trajectory、事件、标注、验证结果和谱系的正确导出；后续仅在源数据具备完整观测通道时增加多模态重组，不虚构缺失观测。

## 待讨论提案：议题 12——全量架构的实施与发布顺序

> 本节贯彻“从一开始建设全量架构”，但仍按纵向闭环逐个验证，里程碑是集成检查点，不是先做一个会被推翻的简化产品。

产品目标已进一步明确为：首次正式版本应是尽量完善、可安装、可持续使用和可验证的完整产品，而不是论文演示、技术原型或只覆盖快乐路径的最小版本。完整性覆盖独立前端、Coding Agent Skill、人工接管、持久任务、故障恢复、CuRobo与SAPIEN闭环、四机器人适配、版本/评估/认证、RoboTwin适配、导出、安装升级和发布证据；不以分布式集群或完整多模态训练数据扩张产品边界。

### 推荐工程结构

```text
apps/web/                  React + TypeScript + R3F独立前端
services/api/              FastAPI、Task Orchestrator、索引与权限
packages/contracts/        JSON Schema/OpenAPI及生成的Python/TS类型
packages/core/             领域模型、谱系、评估与导出门禁
workers/curobo/            CuRobo长生命周期GPU worker
workers/sapien/            SAPIEN/ManiSkill验证worker
skills/coding-agent/       面向用户Coding Agent的配套Skill
robot_packages/            四种机器人适配包与认证资产
validation_scenarios/      场景、任务Oracle和鲁棒性配置
adapters/                  输入与外部导出适配器
tests/                     契约、合成、回归、GPU认证和E2E
deploy/                    Container/Compose与自托管配置
docs/                      架构、用户指南、适配与认证说明
```

1. 前后端类型由同一Schema/OpenAPI生成；机器人、轨迹、Run、评估和导出契约先冻结最小稳定核心，再允许向后兼容扩展。
2. API/Orchestrator先保持模块化单体，CuRobo和SAPIEN作为隔离worker；除非真实负载证明需要，不预先拆分更多服务。
3. AI开发任务采用契约优先：每个任务明确输入输出Schema、允许修改范围、验收样例和测试命令；修改核心Schema必须附迁移和契约测试，避免多个Agent各自发明接口。
4. 所有机器人共用同一管线，形态差异通过Robot Profile、运动组和能力清单表达；禁止为后续机器人复制一套旁路流程。

### 推荐里程碑

#### M0：全量骨架与契约

- 建立上述所有模块和正式部署骨架。
- 完成版本谱系、任务状态、制品存储、执行计划、API、前端壳、Skill壳和两类worker协议。
- 建立CPU CI、前端测试、Schema契约测试和GPU测试入口。

退出条件：前端和Coding Agent均能创建持久任务，提交一个假worker计划，经历Run、Evaluation、Decision和原子Export完整状态链。

#### M1：Panda A1纵向闭环

- 完成标准/映射输入、语义确认、Robot Profile、CuRobo求解、指标、3D回放、候选比较、人工接管和Canonical Export。
- Skill可以驱动完整流程，四个自治挡位具备真实门禁行为。

退出条件：Panda在正向、不可达、越界、碰撞、不连续和语义不明样例上正确通过、失败或升级人工，并达到T1。

#### M2：Panda A2/A3与自动修复

- 加入SAPIEN S0/S1/S2、场景模板、ManiSkill可选任务、碰撞一致性和鲁棒性评估。
- 完成有界ExperimentBatch、自动修复、预算、计划修订、失败恢复和T2/T3认证测试。

退出条件：Panda至少达到T2；是否达到T3由自动修复专项测试决定，不能为了里程碑强行标记。

#### M3：UR5e适配与通用性验证

- 使用同一契约完成UR5e Robot Package、控制器、场景与认证。
- 修复在第二种单臂上暴露的任何Panda专用假设。

退出条件：UR5e达到T1，计划承诺自动直出的范围达到T2；核心管线不存在Panda专用分支。

#### M4：ALOHA多运动组闭环

- 完成双EEF通道、左右臂绑定、同步、臂间碰撞、共享事件与双臂回放/比较。
- 完成适用场景的A2/A3及双臂专项认证。

退出条件：ALOHA至少达到T1，且所有未支持的协作能力在CapabilityManifest和UI中清晰降级，而不是静默近似。

#### M5：第四形态与范围封顶

- 适配已确定的移动或人形代表，只实现规划中明确承诺的运动组、底座或固定底座能力。
- 验证统一Robot Profile是否能表达不同根自由度和形态约束。

退出条件：第四种机器人达到T1；移动、平衡、步态或全身控制等未承诺能力被明确阻断。

#### M6：生态、批量与正式发布

- 完成确认后的外部输入/导出适配器、批任务、缓存、存储清理、远程单机部署、安装与升级。
- 运行冻结认证集、随机压力测试、Agent闭环E2E和四机器人发布验收。
- 生成 `ReleaseEvidenceManifest`、能力矩阵、已知限制和复现说明。

退出条件：四种机器人全部至少T1；承诺自动直出的组合达到T2；官方负向测试硬失败错误放行为零；旧Run和Export在升级后保持可读与可验证。

### 测试与开发工作流

1. 每次提交运行Schema、领域逻辑、前端组件、API和小型合成测试；GPU相关测试分为快速冒烟、夜间/手动回归和发布认证三层。
2. GitHub托管CI不假设免费GPU。正式认证由固定Linux/NVIDIA环境运行并上传签名或带哈希的 `ReleaseEvidenceManifest`。
3. 每个Bug、误放行和跨后端差异都转为版本化回归案例；不允许只修代码而不增加对应判定Oracle。
4. 使用架构决策记录管理会改变契约、依赖、机器人范围或验证声明的决策；普通实现细节不需要为每个改动写ADR。
5. 开源发布同时提供示例数据、最小机器人资产、安装诊断、适配指南、Skill和能力矩阵；无法随仓库再分发的机器人/场景资产提供校验过的获取脚本和许可说明。

### 需要用户确认

## 2026-08-26：对照公开数据集的 v2 草案修订

本轮不涉及产品定位与 §1.4 九条核心属性，只修订 `product-plan-v2.md` 草案中的四处具体契约。

### 触发来源

公开数据集 `simple-world-lab/HiFi-UMI-2K`（LeRobot v3.0 格式、原生 EEF 通道、CC BY 4.0、人手采集的无本体双臂数据）被用作对照实现。其 `meta/info.json` 的 `state_layout` / `action_layout` / `invalid_policy` 字段、以及「坏帧保留行 + 有效性掩码」的做法，暴露了 v2 草案的两处漏项与两处分类不足。

### 新增确认

1. **`MappingSpec` 新增必填字段 `state_action_relation`**，取值 `absolute_next_state` / `independent_command` / `delta_from_state`；两侧语义有差异的通道逐条记入 `divergent_channels`。理由：§2.2 实测发现同名 `gripper` 通道在 `observation.state` 中为关节角弧度、在 `action` 中为归一化指令，按通道名统一映射会静默出错，而原 `MappingSpec` 只有 `coordinate.trajectory_mode`，无法表达这层关系。
2. **语义无法确定时区分 `MISSING` 与 `UNDEFINED`。** `MISSING` 指真值客观存在但未记录（源机器人 FK 派生数据），处理方式是查元数据 / 问人 / 从 `reference` 反推；`UNDEFINED` 指物理上不存在真值（人手采集、无源机器人，世界原点每段任意），处理方式是有限自由度搜索与设计。此前 v2 §3.4 将「参考坐标系身份」一律归入「必须停下来问」，对 `UNDEFINED` 类数据是错误动作。该区分同时明确了 M1「基座变换有限自由度搜索」的服务对象。
3. **导出时本体化失败帧保留行 + 掩码标记，禁止删行。** 新增逐帧列 `valid.retarget` 与逐 episode 列 `retarget.status`，失败帧关节值 carry-forward、掩码置 `false`，掩码须在 `info.json` 的 `features` 段注册为正式通道。理由：删行会破坏与 mp4 帧、`timestamp`、`frame_index` 的对齐，使 §7.1「只动表不动 mp4」的前提失效；而 carry-forward 后的无效帧外观上是合理位姿，只有掩码能区分。
4. **`meta/stats.json` 必须重算，且在按 `valid.retarget == true` 过滤之后算。** 原 §7.1 重写清单遗漏该文件。继承源数据集统计量等于用源机器人分布归一化目标机器人关节值，属不报错的静默错误。

### 附带约定

源数据集若自带机器可读的语义声明块（如 LeRobot v3 `meta/info.json` 的 `state_layout` / `action_layout`），`DataAdapter` 直接读取并标证据等级 `EXPLICIT`，不进 AI 推断路径；对称地，本工具导出的 `retarget` 元数据段按同一粒度写出，使下游同样免于推断。

### 本轮明确不纳入

1. `HiFi-UMI-2K` 不作为 M1 材料。它是双臂、无源关节真值，§10.2 源关节 FK 交叉校验与 §10.3 真实往返验证均不适用，且不填补单臂数据缺口。定位为 M3 之后的广度案例与「无源本体」极端样本。
2. §10.3 三层测试资产表未按「弱无本体（源机器人 FK 派生，有 `reference` 可自检）／强无本体（人手采集，无任何关节真值）」重新分层，留待后续讨论。
3. 同时导出 GR00T `modality.json` 以扩大训练框架兼容面，留待后续讨论。

`simple-world-lab` 是否发布过配套工具链代码。已核查其 HuggingFace 组织下仅有该数据集一个仓库、数据集 README 内无任何代码仓库链接，未做全网检索。当前判断为「官方渠道未提供」，非「确认无代码」。
